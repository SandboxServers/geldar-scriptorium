## SC-76: the world port 18443 (owner decision 2026-11-09, decision 34)

**Why.** The real world's MCP is served on public port 18443 over TLS. Today the validator accepts only 80 and 443 (`valid_mcp_url` in `player.sh`, `player.ps1`) and Squid allows only `Safe_ports` 80 and 443. The change must widen exactly one thing: one port, set by the owner in `world.conf`, for one host, the host of `mcp_base`.

**The rule (the contract all four packets build against).**

1. `launcher/config/world.conf` gets the key `mcp_port` (owner-set; blank means only 80 and 443 are ever accepted). Valid value: digits only, no leading zero, 1024 to 65535. Anything else is treated as blank.
2. `valid_mcp_url` accepts an explicit port other than 80 and 443 **only if all of these hold**: `mcp_port` is valid; the URL's port equals it (digits compared as text); `mcp_base` is non-blank and has exactly the shape `scheme://host` or `scheme://host:port` (scheme `http` or `https`, no userinfo, path, query, fragment or whitespace; anything else counts as blank); **the URL's scheme equals the scheme of `mcp_base`**; and the URL's host equals the host of `mcp_base`, compared case-sensitively (`-ceq` in PowerShell) after both pass the existing host rules (the port part of `mcp_base` is ignored in the comparison). Port digits are `[0-9]` in both twins (in PowerShell `\d` also matches digits of other scripts, so it is not used). The rule reads `world.conf` as data (never sourced) with `world_conf` / `Get-WorldConf`, through the human seam `GELDAR_SHARE` that tests already use, and only when a non-default port is present. **Where the readers live:** today `world_conf` is in `new.sh` and `share_dir` in `session.sh` (and their PowerShell twins), which `urlSuite` and `runLib` do not load (they load `common.*` and `player.*`). SC-76c and SC-76d therefore move `share_dir` / `Get-ShareDir` and `world_conf` / `Get-WorldConf` unchanged into `common.sh` / `common.ps1`. `valid_mcp_url` / `Test-McpUrl` **fail closed**: if the reader function is missing (`type world_conf`, `Get-Command Get-WorldConf`) or the file cannot be read, a non-default port is refused. The port in `player.json` can never widen anything: it is compared with a value the launcher read from its own shipped config.
3. The session gets the **effective port** of the world URL in a one-line file `pub/allowlist-world-ports.txt` (the explicit port, or 80 for `http` and 443 for `https` when none is given) next to `pub/allowlist-world.txt`, 0644 in the 0755 `pub/` like it. The file always holds the URL's effective port, so the proxy opens exactly that host and exactly that port. The launcher exports its path as `GELDAR_WORLD_PORTS` to `compose`. The compose file mounts it at `/etc/squid/allowlist-world-ports.txt`, with a default of `image/proxy/world-ports-default.txt` (one line, `443`) so the image tests and any compose run without the launcher keep working.
4. Squid (written exactly so; `(V)` = the coder confirms the syntax with `squid -k parse` in the pinned Squid, as `proxy-config.test.ts` does): `acl world_port port "/etc/squid/allowlist-world-ports.txt"` and `acl port_80 port 80`, then, in this order: `http_access deny !Safe_ports !world_port`, `http_access deny CONNECT port_80`, `http_access deny CONNECT !SSL_ports !world_port`, `http_access allow allowed_vendor Safe_ports`, `http_access allow allowed_world world_port`, `http_access deny all`. The old `allow allowed_world Safe_ports` line is **removed**: it would keep ports 80 and 443 open on the world host whatever the ports file says. The effect: the vendor hosts keep 80 and 443; the world host is open on exactly the one port in its ports file (which the launcher sets to the URL's effective port) and on nothing else; a CONNECT to port 80 is refused for every host (`deny CONNECT port_80` closes the hole that `!world_port` would otherwise open when the mock world is plain http on 80); a CONNECT to the world port is allowed (this is how TLS reaches 18443). This narrows today's rule (the world host on 80 with an `https` URL is no longer open). If the `"file"` form is not accepted for `port` ACLs (V), fall back to an `include /etc/squid/world-access.conf` file that the launcher writes from the validated number; the card's tests stay the same.
5. No new message key: a refused port is `bad_url` (for `new`) or `pj_fail ... 'mcp_url'` (for a player.json), as today.

## SC-75: the local-world dev override (decision 33; owner decision relayed 2026-11-09: test the MCP on loopback first)

**Why.** Ranger number one is tested against a real MCP server on the owner's own machine before the public name exists. `player.json` is hostile input, so the validator is not relaxed (SC-60m and SC-60n refuse local and private names, and stay that way). Instead one human-environment seam names the dev world; it is never read from `player.json` or any repository file.

**Rules (the contract).**

1. The seam is the environment variable `GELDAR_DEV_MCP_URL`, set by the human in the shell that runs `geldar-play`. It is a human seam (like `GELDAR_STATE_DIR`): ungated, classified in `seams.json` by SC-76a, documented in the launcher README by SC-70d, and never passed into the session container.
2. When set, its value must match **exactly** `http://host.docker.internal:<port>/p/<player_id>` with port 1024 to 65535 (digits, no leading zero) and `<player_id>` equal to the id of the player being started. Lowercase only; no userinfo, query, fragment, trailing slash, whitespace or other path. A set but invalid value is a refusal (`dev_world_bad`, status 1, no docker call), never silently ignored.
3. It applies only to a single-player `play` or `setup`. With two or more ids and the variable set, `play` refuses (`dev_world_single`) so one URL cannot reach a second player.
4. `player.json` is still read and validated as today (its `mcp_url` must pass `valid_mcp_url`). The dev URL replaces only the `GELDAR_MCP_URL` value passed to the session and the world allowlist for that launch. **The hook passes the dev URL straight to the allowlist writer**, which never validates (it writes what it is given); `valid_mcp_url` still refuses `host.docker.internal`, so the dev hook must not route the dev URL through it. The only check on the dev URL is the exact-shape rule 2 in `devworld.*`. `write_allowlist` receives host `host.docker.internal` and the port, so `pub/allowlist-world.txt` is exactly `host.docker.internal` and `pub/allowlist-world-ports.txt` exactly the port (SC-76's mechanism, no new Squid rule).
5. The launcher-written `override.yml` gains, only when the seam is active, a `proxy` service block with `extra_hosts: ["host.docker.internal:host-gateway"]` (Docker Desktop resolves the name natively; a Linux engine needs it). **The guide must warn** that on a Linux engine the local MCP must listen on `0.0.0.0` or the bridge gateway address to be reachable from the proxy container, which exposes it to the local network unless a firewall blocks it; prefer the bridge gateway address. With the seam unset, `override.yml` is byte-identical to today's.
6. Every launch with the seam active prints `dev_world_active` to stderr first (a loud, plain line naming the URL and how to turn it off). The seam is read at launch only: nothing is persisted in the state dir, `player.json` or the clone.
7. The bearer token is the player's stored token. **It travels in clear over http to whatever listens on the dev port on the host**, so the guide advises a separate dev token minted for the test and given with `--token-file`, never the token for the real world. The launcher does not check this (it cannot tell which world a token belongs to).
