### SC-63c: The workflow check (gate for strand C)

- **Branch** `scriptorium/sc-63c-workflow-check`, worktree `sc-63c`. Commit: `test(repo-checks): lint workflows for pins, permissions, triggers, secret handling and model use`. Model: Sonnet. Depends on: wave 5.
- **Files (5; plus the lockfile, rule 13):** `tools/repo-checks/src/workflows.ts` (new), `tools/repo-checks/src/workflows.test.ts` (new), `tools/repo-checks/src/workflows-cli.ts` (new, prints findings, exit 1), `tools/repo-checks/package.json` (add dependency `yaml` `2.9.1`: `./scriptorium.ps1 pnpm add -E yaml@2.9.1 --filter @geldar/repo-checks`), `package.json` (root; one script `check:workflows`: `node tools/repo-checks/src/workflows-cli.ts`, and `scriptorium.ps1`'s check list is **not** edited here: the wave's one `check` runs `check:workflows` through CI only, and SC-63f adds the step to `ci.yml`; sole owners per the shared-files table). `pnpm-lock.yaml` is regenerated by `merge-packet`.
- **`workflows.ts`:** `checkWorkflow(file: {path, text}): Finding[]` (pure; the cli reads `.github/workflows/*.yml` and `*.yaml`). It parses with `yaml` (`parseDocument`, rejecting duplicate keys and anchors/aliases in a workflow). Rules, each a named finding:
  1. `pin`: every `uses:` is `owner/repo[/path]@<40 lowercase hex>` followed on the same line by a comment `# v<semver>` (a local `./...` reusable workflow is allowed; `docker://` is refused). A tag, a branch, a short SHA or an uppercase SHA is a finding.
  2. `permissions`: a top-level `permissions` key exists and is a mapping (never `write-all`, never absent); every job that sets `id-token: write` is in a workflow listed in a constant `ID_TOKEN_ALLOWED = ['publish-template.yml', 'release.yml']`; `packages: write` only in `release.yml`; `contents: write` only in the `release` job of `release.yml` (a second constant); `ci.yml`, `publish-template.yml` and `image-scan.yml` never have it.
  3. `triggers` (applies to `publish-template.yml` and `release.yml`): `on` contains only `push` with `tags` exactly `['kit-v*']` and no `branches`, or `workflow_call`, or `workflow_dispatch` where the file's constant allows it (`publish-template.yml` allows it for the dry run only, and its credentialed job must carry `if: github.event_name == 'push'`); never `pull_request`, `pull_request_target`, `schedule`, `issue_comment`, `workflow_run` or `repository_dispatch`.
  4. `secrets`: no `secrets.<name>` other than `secrets.GITHUB_TOKEN` anywhere (D-SC-02: nothing in GitHub secrets); no `secrets: inherit`.
  5. `model`: no workflow mentions `ANTHROPIC`, `CLAUDE_CODE`, `OPENAI`, an `anthropics/` or `openai/` action, the command `claude` as a word in a `run:`, or the verb `live-check` (D-SC-01: no model call in CI).
  6. `mask`: in a `run:` step that calls `az keyvault secret show` (or `az keyvault secret download`), the text `::add-mask::` appears **before** the first write to `$GITHUB_OUTPUT`, `$GITHUB_ENV` or `$GITHUB_STEP_SUMMARY`, and no `echo`/`printf`/`cat` prints the variable that holds the secret to stdout without a following mask (a line-based heuristic; the finding names the line); `set -x` and `bash -x` are findings in such a step.
  7. `injection`: no `run:` block contains `${{ github.event.`, `${{ github.head_ref }}`, `${{ inputs.` or `${{ steps.*.outputs.` text: values reach shell through `env:` only.
  8. `checkout`: in `publish-template.yml` and `release.yml` every `actions/checkout` has `persist-credentials: false`.
  9. `timeout`: every job has `timeout-minutes`.
  10. `tagguard`: in `publish-template.yml` and `release.yml` the first job step after checkout contains `git merge-base --is-ancestor` against `origin/main` (a tag on a commit that is not on `main` must not release), and the checkout has `fetch-depth: 0`.
  `ci.yml` is held to rules 1, 2 (top-level only), 4, 5, 7, 9 and not to the release-only rules (8, 10 and the triggers rule).
- **Tests (`workflows.test.ts`, fixtures as strings):** for each rule one passing and several hostile workflows: an unpinned `@v4`, `@main`, a 39-hex pin, a pin without the version comment, an uppercase SHA; `permissions: write-all`; `id-token: write` in `ci.yml`; `pull_request_target` in a release file; `push: branches: [main]` in a release file; `secrets.AZURE_CLIENT_SECRET`; a step with `ANTHROPIC_API_KEY`, one with `uses: anthropics/claude-code-action@...`, one with `run: claude -p hi`, one with `run: ./scriptorium.ps1 live-check`; a Key Vault step that writes `GITHUB_OUTPUT` before masking and one with `set -x`; `${{ github.event.pull_request.title }}` inside `run:`; a checkout without `persist-credentials: false`; a job without `timeout-minutes`; a release job with no merge-base guard; a YAML file with an anchor or a duplicate key; invalid YAML (a finding, never a crash). Plus: the real workflows in the repo (`ci.yml`) pass with zero findings; `workflows-cli.ts` exits 1 on a fixture directory with a finding (`spawnSync` on a temp dir) and 0 on `ci.yml`.
- **Revert checks:** remove each rule's check one at a time: its hostile fixture stops failing the way the test expects (one `it.each` row per rule proves that).
- **Checks:** `./scriptorium.ps1 pnpm vitest run tools/repo-checks/src/workflows.test.ts`, `./scriptorium.ps1 pnpm check:workflows`, `format`, `typecheck`.

### SC-63b: The template publish tool

- **Branch** `scriptorium/sc-63b-publish-tool`, worktree `sc-63b`. Commit: `feat(release): add the template publish tool with a dry-run mode`. Model: Sonnet. Depends on: wave 5. Parallel with SC-63c. Also a gate: it creates the `tools/release` package skeleton that SC-63e uses.
- **Files (4):** `tools/release/package.json` (private workspace package `@geldar/scriptorium-release`, no dependencies, script `typecheck`), `tools/release/tsconfig.json`, `tools/release/src/publish-template.ts`, `tools/release/src/publish-template.test.ts`.
- **Command:** `node tools/release/src/publish-template.ts --version kit-vX.Y.Z --source-sha <40 hex> [--image <repo>@sha256:<64 hex>] [--remote <url>] [--template template] [--branch main] [--dry-run]`. Plain Node (`node:child_process`, `node:fs`), real `git`. Token only from the environment variable `GELDAR_PUBLISH_TOKEN`.
- **Behaviour (in this order; every failure exits 1 with one line and nothing pushed):**
  1. Validate the arguments: `--version` matches `^kit-v(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)(-[0-9A-Za-z.]+)?$`; `--image` matches the launcher's digest regex; `--source-sha` is 40 lowercase hex; the default remote is `https://github.com/SandboxServers/geldar-player-template.git`, and any other remote is refused unless `GELDAR_INTERNAL=1` (tests use a local bare repo), so the token cannot be sent to another host; a token is refused for a non-https remote.
  2. Read `--template` (default `template/`): refuse a symlink, a file over 1 MiB, more than 200 files, a path with `..`, a backslash, a leading `.git` component, or a CR byte in a text file (LF only, `.gitattributes`). Copy to a temp work tree. In the copy, `player.json` gets `kit_version` = the version without the `kit-v` prefix and, if `--image` is given, `kit_image` = the image; every other key is unchanged; the result is validated against `schemas/player.schema.json`'s patterns (the tool reads the schema file, no `ajv`: it checks the two patterns it edits). Without `--image` the file keeps the empty `kit_image` (the state SC-63a publishes before the image job exists).
  3. Clone the remote's `--branch` into a second temp dir with `-c core.hooksPath=/dev/null -c fetch.fsckObjects=true`, `GIT_TERMINAL_PROMPT=0`, no tags needed; an empty remote (first publish) is allowed. Replace the working tree with the assembled tree exactly (delete files not in the assembled set; keep nothing from the old tree), `git add -A`.
  4. Commit as `geldar-bot <geldar-bot@users.noreply.github.com>` with `--allow-empty` (every release maps to one commit) and the message: first line `release <version>`, a blank line, then exactly three lines `template: <source-sha>`, `image: <digest or none>`, `launcher: <version>` (the release triple; the image line is the digest `sha256:...` only).
  5. Tag the commit `<version>` in the clone (annotated, same identity). If the tag already exists on the remote with a different commit: refuse (never move a tag); with the same tree and message: exit 0 `already published` and do nothing.
  6. **`--dry-run`: stop here.** Print the commit's `git show --stat`, the message and the planned push refspecs; exit 0. A dry run never contacts a remote: with a URL remote, step 3 is replaced by `git init` of an empty work repo (so the printed stat shows the whole tree); with a local path (tests) it clones normally.
  7. Otherwise push `HEAD:refs/heads/<branch>` and the tag, **without force** (`git push` with no `--force`, no `+`), using the token through the environment: `GIT_CONFIG_COUNT=1`, `GIT_CONFIG_KEY_0=http.https://github.com/.extraheader`, `GIT_CONFIG_VALUE_0=Authorization: Basic <base64 of x-access-token:<token>>`; the token is never on an argv, in the remote URL or in `.git/config`, and the tool prints `::add-mask::<value>` for the token and its base64 before any git call when `GITHUB_ACTIONS` is set. A rejected push (non-fast-forward: someone edited the template by hand) exits 1 with the line `the template repository moved; nobody edits it by hand`.
- **Tests (`GELDAR_INTERNAL=1`, local bare repos, 60_000 each; no network):** assembled tree equals `template/` plus the two `player.json` edits (byte compare of every other file); one commit, message lines exact, identity exact, tag created; a second publish with a new version is a fast-forward child (history length 2); the same version twice is `already published` and the remote unchanged; same tag with a different tree is refused; `--dry-run` leaves the bare repo's refs unchanged and exits 0 (compare `for-each-ref` before and after) and prints the stat; `--image` with a tag form, a bad version, a bad SHA, a non-allowed remote without `GELDAR_INTERNAL` are refused with nothing created; hostile templates (a symlink, a `.git/config` file, a 2 MiB file, a CRLF file, 201 files) are refused; a remote that moved is refused without force (assert no `+` and no `--force` in the argv log of a `git` shim placed first on `PATH` that logs and then execs the real git); the token (a recognisable string) appears in no stdout, stderr, argv log, remote URL or `.git/config` of either temp dir, and `::add-mask::` lines appear under `GITHUB_ACTIONS=true`; the temp dirs are removed on success and on failure.
- **Revert checks:** add `--force` to the push: the moved-remote case fails. Put the token in the URL: the token case fails. Drop `--allow-empty`: the identical-template second release case fails (no commit). Skip the schema pattern: the bad-image case fails.
- **Checks:** `./scriptorium.ps1 pnpm vitest run tools/release`, `format`, `typecheck`.

## SC-64: `geldar-play upgrade`
