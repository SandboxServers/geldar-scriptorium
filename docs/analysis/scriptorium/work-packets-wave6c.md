### SC-63c: The workflow check (gate for strand C)

- **Branch** `scriptorium/sc-63c-workflow-check`, worktree `sc-63c`. Commit: `test(repo-checks): lint workflows for pins, permissions, triggers, secret handling and model use`. Model: Sonnet. Depends on: wave 5.
- **Files (5; plus the lockfile, rule 13):** `tools/repo-checks/src/workflows.ts` (new), `tools/repo-checks/src/workflows.test.ts` (new), `tools/repo-checks/src/workflows-cli.ts` (new, prints findings, exit 1), `tools/repo-checks/package.json` (add dependency `yaml` `2.9.1`: `./scriptorium.ps1 pnpm add -E yaml@2.9.1 --filter @geldar/repo-checks`), `package.json` (root; one script `check:workflows`: `node tools/repo-checks/src/workflows-cli.ts`; `scriptorium.ps1`'s check list is **not** edited here (SC-62b owns that file), and this is a recorded exception to "`check` is everything CI runs": `check:workflows` and actionlint run in CI only, and SC-63i says so in `docs/release.md` (a developer runs `./scriptorium.ps1 pnpm check:workflows` by hand before changing a workflow); and `ci.yml` is SC-63h's; sole owners per the shared-files table). `pnpm-lock.yaml` is regenerated by `merge-packet`.
- **`workflows.ts`:** `checkWorkflow(file: {path, text}): Finding[]` (pure; the cli reads `.github/workflows/*.yml` and `*.yaml`). It parses with `yaml` (`parseDocument`, rejecting duplicate keys and anchors/aliases in a workflow). A job is **credentialed** when it sets `id-token: write`, `packages: write` or `contents: write`. Rules, each a named finding:
  1. `pin`: every `uses:` is `owner/repo[/path]@<40 lowercase hex>` followed on the same line by a comment `# v<semver>` (a local `./...` reusable workflow is allowed; `docker://` is refused). A tag, a branch, a short SHA or an uppercase SHA is a finding.
  2. `permissions`: a top-level `permissions` key exists and is a mapping (never `write-all`, never absent). Constants, one per kind, each a map from workflow file to the job names that may hold it: `ID_TOKEN_JOBS = {'publish-template.yml': ['publish'], 'release.yml': ['sign', 'launcher', 'template']}`, `PACKAGES_WRITE_JOBS = {'release.yml': ['build', 'sign']}`, `CONTENTS_WRITE_JOBS = {'release.yml': ['release']}`; any other job (and every job of `ci.yml`, `image-scan.yml`) that sets one is a finding. **`idtoken-uses`:** in a job that sets `id-token: write` (or `packages: write`), every `uses:` must be in `ACTIONS_WITH_CREDENTIALS = actions/checkout, actions/setup-node, actions/download-artifact, actions/upload-artifact, sigstore/cosign-installer, azure/login, actions/create-github-app-token` (plus `docker/*` for a `packages: write` job that has no `id-token`, and a local `./.github/workflows/...` call); `aquasecurity/*` and `anchore/*` actions never appear in a credentialed job. (The release `sign` job holds both `packages: write` and `id-token: write`, so docker actions are not allowed there.)
  3. `triggers`. **3a, every workflow:** never `pull_request_target`, `workflow_run`, `issue_comment` or `repository_dispatch`. **3b, `publish-template.yml` and `release.yml`:** `publish-template.yml` has only `workflow_call` and `workflow_dispatch`; `release.yml` has only `push` with `tags` exactly `['kit-v*']` and no `branches`, plus `workflow_dispatch` (the rehearsal); never `pull_request`, `schedule` in these two. **Every credentialed job carries `if: github.event_name == 'push' && startsWith(github.ref, 'refs/tags/kit-v')` (plus the repository clause where the card says so).** In a called workflow the `github` context is the caller's, so `github.event_name` is `push` there; **the string `workflow_call` must not appear in any `if:` expression** (it would never be true, and the publish would be silently skipped): `no-workflow-call-if` is a finding.
  4. `secrets`: no `secrets.<name>` other than `secrets.GITHUB_TOKEN` anywhere (D-SC-02: nothing in GitHub secrets); no `secrets: inherit`. No workflow text mentions `GELDAR_INTERNAL` or `GELDAR_UNSAFE_IMAGE` (`GELDAR_INTERNAL=1` lets the publish tool send a token to another remote).
  5. `model`: no workflow mentions `ANTHROPIC`, `CLAUDE_CODE`, `OPENAI`, an `anthropics/` or `openai/` action, the command `claude` as a word in a `run:`, or the verb `live-check` (D-SC-01: no model call in CI).
  6. `mask`: in a `run:` step that calls `az keyvault secret show` (or `az keyvault secret download`), the text `::add-mask::` appears **before** the first write to `$GITHUB_OUTPUT`, `$GITHUB_ENV` or `$GITHUB_STEP_SUMMARY`, and no `echo`/`printf`/`cat` prints the variable that holds the secret to stdout without a following mask (a line-based heuristic; the finding names the line); `set -x` and `bash -x` are findings in such a step.
  7. `injection`: **any `${{` inside a `run:` string is a finding (zero allowed).** Values reach the shell only through `env:`. Hostile fixtures: `run: echo ${{ github.ref_name }}` (a tag such as `kit-v1.0.0$(id)` matches `kit-v*`, git allows `$ ( )`), `run: echo ${{ needs.build.outputs.digest }}`, `run: echo ${{ github.event.pull_request.title }}`, `run: echo ${{ inputs.version }}`, `run: echo ${{ env.VERSION }}`, `run: echo ${{ vars.X }}`.
  8. `checkout`: in `publish-template.yml` and `release.yml` every `actions/checkout` has `persist-credentials: false`.
  9. `timeout`: every job has `timeout-minutes` (a job that is a `uses:` call is exempt).
  10. `tagguard`: in `publish-template.yml` and `release.yml` the first job that has a credentialed successor contains, after checkout, a step with `git merge-base --is-ancestor` against `origin/main` (a tag on a commit that is not on `main` must not release), and the checkout has `fetch-depth: 0`. This catches mistakes; it is not a defence against someone who can edit the workflow in the tagged commit (see the owner decision on tag creation).
  `ci.yml` is held to rules 1, 2 (top-level only), 3a, 4, 5, 7, 9 and not to the release-only rules (3b, 8, 10).
- **Tests (`workflows.test.ts`, fixtures as strings):** for each rule one passing and several hostile workflows: an unpinned `@v4`, `@main`, a 39-hex pin, a pin without the version comment, an uppercase SHA; `permissions: write-all`; `id-token: write` in `ci.yml`; `id-token: write` in a job named `build`; a `docker/login-action` use in a job with `id-token: write`; `aquasecurity/trivy-action` in a job with `packages: write`; `pull_request_target` in `ci.yml` and in a release file; `push: branches: [main]` in a release file; an `if:` containing `github.event_name == 'workflow_call'`; a credentialed job without the tag `if`; `secrets.AZURE_CLIENT_SECRET`; a step with `GELDAR_INTERNAL`; a step with `ANTHROPIC_API_KEY`, one with `uses: anthropics/claude-code-action@...`, one with `run: claude -p hi`, one with `run: ./scriptorium.ps1 live-check`; a Key Vault step that writes `GITHUB_OUTPUT` before masking and one with `set -x`; the injection fixtures above; a checkout without `persist-credentials: false`; a job without `timeout-minutes`; a release job with no merge-base guard; a YAML file with an anchor or a duplicate key; invalid YAML (a finding, never a crash). Plus: the real workflows in the repo (`ci.yml`) pass with zero findings (its `${{ }}` values are in `env:` and `concurrency`, none in `run:`); `workflows-cli.ts` exits 1 on a fixture directory with a finding (`spawnSync` on a temp dir) and 0 on `ci.yml`.
- **Revert checks:** remove each rule's check one at a time: its hostile fixture stops failing the way the test expects (one `it.each` row per rule proves that).
- **Checks:** `./scriptorium.ps1 pnpm vitest run tools/repo-checks/src/workflows.test.ts`, `./scriptorium.ps1 pnpm check:workflows`, `format`, `typecheck`.

### SC-63b: The template publish tool

- **Branch** `scriptorium/sc-63b-publish-tool`, worktree `sc-63b`. Commit: `feat(release): add the template publish tool with a dry-run mode`. Model: Sonnet. Depends on: wave 5. Parallel with SC-63c. Also a gate: it creates the `tools/release` package skeleton that SC-63e uses.
- **Files (4):** `tools/release/package.json` (private workspace package `@geldar/scriptorium-release`, no dependencies, script `typecheck`), `tools/release/tsconfig.json`, `tools/release/src/publish-template.ts`, `tools/release/src/publish-template.test.ts`.
- **Command:** `node tools/release/src/publish-template.ts --version kit-vX.Y.Z --source-sha <40 hex> [--image <repo>@sha256:<64 hex>] [--remote <url>] [--template template] [--branch main] [--dry-run]`. Plain Node (`node:child_process`, `node:fs`), real `git`. Token only from the environment variable `GELDAR_PUBLISH_TOKEN`. A version with a hyphen (`kit-v0.1.0-rc1`) is a prerelease: it is published like any other (one commit, one tag), and the workflow marks the GitHub release as a prerelease (SC-63f).
- **Behaviour (in this order; every failure exits 1 with one line and nothing pushed):**
  1. Validate the arguments: `--version` matches `^kit-v(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)(-[0-9A-Za-z.]+)?$`; `--image` matches the launcher's digest regex; `--source-sha` is 40 lowercase hex; the default remote is `https://github.com/SandboxServers/geldar-player-template.git`, and any other remote is refused unless `GELDAR_INTERNAL=1` (tests use a local bare repo), so the token cannot be sent to another host; a token is refused for a non-https remote.
  2. Read `--template` (default `template/`): refuse a symlink, a file over 1 MiB, more than 200 files, a path with `..`, a backslash, a leading `.git` component, or a CR byte in a text file (LF only, `.gitattributes`). Copy to a temp work tree. In the copy, `player.json` gets `kit_version` = the version without the `kit-v` prefix and, if `--image` is given, `kit_image` = the image; every other key is unchanged; the result is validated against `schemas/player.schema.json`'s patterns (the tool reads the schema file, no `ajv`: it checks the two patterns it edits). Without `--image` the file keeps the empty `kit_image`.
  3. Clone the remote's `--branch` into a second temp dir with `-c core.hooksPath=<an empty temp directory>` (not `/dev/null`: unreliable with Windows git, and the tests run on Windows dev machines) `-c fetch.fsckObjects=true`, `GIT_TERMINAL_PROMPT=0`, no tags needed; an empty remote (first publish) is allowed. Replace the working tree with the assembled tree exactly (delete files not in the assembled set; keep nothing from the old tree), `git add -A`.
  4. Commit as `geldar-bot <geldar-bot@users.noreply.github.com>` with `--allow-empty` (every release maps to one commit) and the message: first line `release <version>`, a blank line, then exactly three lines `template: <source-sha>`, `image: <digest or none>`, `launcher: <version>` (the release triple; the image line is the digest `sha256:...` only).
  5. Tag the commit `<version>` in the clone (annotated, same identity). If the tag already exists on the remote with a different commit: refuse (never move a tag); with the same tree and message: exit 0 `already published` and do nothing.
  6. **`--dry-run`: stop here.** Print the commit's `git show --stat`, the message and the planned push refspecs; exit 0. A dry run never contacts a remote: with a URL remote, step 3 is replaced by `git init` of an empty work repo (so the printed stat shows the whole tree); with a local path (tests) it clones normally.
  7. Otherwise push `HEAD:refs/heads/<branch>` and the tag, **without force** (`git push` with no `--force`, no `+`), using the token through the environment: `GIT_CONFIG_COUNT=1`, `GIT_CONFIG_KEY_0=http.https://github.com/.extraheader`, `GIT_CONFIG_VALUE_0=Authorization: Basic <base64 of x-access-token:<token>>`; the token is never on an argv, in the remote URL or in `.git/config`, and the tool prints `::add-mask::<value>` for the token and its base64 before any git call when `GITHUB_ACTIONS` is set. A rejected push (non-fast-forward: someone edited the template by hand) exits 1 with the line `the template repository moved; nobody edits it by hand`.
- **Tests (`GELDAR_INTERNAL=1`, local bare repos, 60_000 each; no network):** assembled tree equals `template/` plus the two `player.json` edits (byte compare of every other file); one commit, message lines exact, identity exact, tag created; a prerelease version (`kit-v0.1.0-rc1`) publishes; a second publish with a new version is a fast-forward child (history length 2); the same version twice is `already published` and the remote unchanged; same tag with a different tree is refused; `--dry-run` leaves the bare repo's refs unchanged and exits 0 (compare `for-each-ref` before and after) and prints the stat; `--image` with a tag form, a bad version, a bad SHA, a non-allowed remote without `GELDAR_INTERNAL` are refused with nothing created; hostile templates (a symlink, a `.git/config` file, a 2 MiB file, a CRLF file, 201 files) are refused; a remote that moved is refused without force (assert no `+` and no `--force` in the argv log of a `git` shim placed first on `PATH` that logs and then execs the real git); the token (a recognisable string) appears in no stdout, stderr, argv log, remote URL or `.git/config` of either temp dir, and `::add-mask::` lines appear under `GITHUB_ACTIONS=true`; the temp dirs are removed on success and on failure.
- **Revert checks:** add `--force` to the push: the moved-remote case fails. Put the token in the URL: the token case fails. Drop `--allow-empty`: the identical-template second release case fails (no commit). Skip the schema pattern: the bad-image case fails.
- **Checks:** `./scriptorium.ps1 pnpm vitest run tools/release`, `format`, `typecheck`.

### SC-63a: The template publish workflow

- **Branch** `scriptorium/sc-63a-publish-workflow`, worktree `sc-63a`. Commit: `ci(release): publish template/ to geldar-player-template through Azure OIDC and Key Vault, called from the release workflow`. Model: Sonnet. Depends on: SC-63b, SC-63c.

- **Workflow (final form; SC-63f does not edit this file):** `name: publish-template`; `on: workflow_call` (inputs `version` string required, `image` string required (the digest reference `repo@sha256:...`), `source-sha` string required) and `workflow_dispatch` (a dry run on any ref, no credential); top-level `permissions: {}` (empty); `concurrency: {group: publish-template-${{ github.ref }}, cancel-in-progress: false}`. Values from inputs reach the shell only through `env:` (`VERSION: ${{ inputs.version || 'kit-v0.0.0-dryrun' }}`, `IMAGE: ${{ inputs.image }}`, `SOURCE_SHA: ${{ inputs.source-sha || github.sha }}`).
  - **Job `assemble` (dry run; runs on both triggers; `permissions: contents: read`; `timeout-minutes: 10`; no Azure, no secret):** checkout (pinned, `persist-credentials: false`, `fetch-depth: 0`); the tag guard step (`git merge-base --is-ancestor "$GITHUB_SHA" origin/main`, skipped on dispatch where there is no tag); `actions/setup-node` with `.nvmrc`; `node tools/release/src/publish-template.ts --dry-run --version "$VERSION" --source-sha "$SOURCE_SHA"`.
  - **Job `publish` (`needs: assemble`; `if: github.event_name == 'push' && startsWith(github.ref, 'refs/tags/kit-v') && github.repository == 'SandboxServers/geldar-scriptorium'`; `environment` none; `permissions: {id-token: write, contents: read}` and nothing else; `timeout-minutes: 15`).** **Why `push`:** in a called workflow `github.event_name` and `github.ref` are the caller's, so for a run started by the tag push they are `push` and the tag ref; the value `workflow_call` never occurs there, and a condition on it (the first draft of SC-63f) would silently skip the publish while the calling `template` job still reports success. Steps: (1) checkout as above and the same tag guard; (2) `azure/login` with `client-id: ${{ vars.AZURE_CLIENT_ID }}`, `tenant-id: ${{ vars.AZURE_TENANT_ID }}`, `subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}`; (3) step `keyvault`: one `run:` with `set +x`, `set -euo pipefail`, reads `geldar-bot-app-id` and `geldar-bot-private-key` from the vault named by `env: KV: ${{ vars.KEY_VAULT_NAME }}` with `az keyvault secret show --vault-name "$KV" --name <n> --query value --output tsv`; **masks first**: `echo "::add-mask::$app_id"`, then each line of the key (`while IFS= read -r l; do [ -n "$l" ] && echo "::add-mask::$l"; done`), then the whole value; only then writes `app-id=...` and the multi-line `private-key` (random heredoc delimiter) to `$GITHUB_OUTPUT`; (4) `actions/create-github-app-token` (pinned) with `app-id: ${{ steps.keyvault.outputs.app-id }}`, `private-key: ${{ steps.keyvault.outputs.private-key }}`, `owner: SandboxServers`, `repositories: geldar-player-template`, `permission-contents: write`, `permission-metadata: read` (so the token cannot be wider than the App's installation even if it were); (5) `az logout` with `if: always()`; (6) setup-node, then `node tools/release/src/publish-template.ts --version "$VERSION" --source-sha "$SOURCE_SHA" --image "$IMAGE"` with `env: GELDAR_PUBLISH_TOKEN: ${{ steps.app.outputs.token }}` only on that step.
  - Not in the file: `pull_request`, `push`, branch triggers, `secrets.*`, a bare token in `run:`, `ACTIONS_STEP_DEBUG` use, a cache step, an artifact upload.
