# Scriptorium work packets: wave 14 (the persistent player container)

Part of [work-packets.md](work-packets.md) (dispatch rules 1-24). Ledger: [README.md](README.md). Written 2026-11-11 from the owner's instruction (decision 64). Builds on waves 11 and 12 (the supervisor, the director), SC-140 (the shared Claude login) and SC-141 (`new --repo`).

**The owner's requirement.** A player is a persistent thing, not a series of throwaway sessions. The player repo is checked out into the player's container and persisted there; everything about the player runs from the container; it pushes back to its repo on a regular schedule; the supervisor and director (the orchestrator) run inside and take care of it as the player plays. Chosen by the owner (2026-11-11): the push credential is a per-player **deploy key held in the container**, and Kimberly (`ag-kimberly-01`, repo `SandboxServers/player-mmpr-pink`) waits for this to exist.

**What changes from today.** Today (waves 0 to 11) each `play` or `run` cycle starts a throwaway session container; the host holds the credentials, does the clone, runs the post-session gate in a network-less helper container and pushes. That kept every GitHub credential out of anything the character shares a container with. This wave moves the gate and the push into the player's own container group, so the security argument has to be rebuilt, not dropped: see the design.

## Design (decision 64)

**The group.** `geldar-play start <id>` brings up one compose project, `geldar-<id>`, with `restart: unless-stopped`, four services:

| Service | Runs | Network | Holds |
|---|---|---|---|
| `player` | the in-container supervisor (PID 1, user `supervisor`) and, as children, the headless character sessions (user `player`, uid 1000) and the director calls | `inside`, through `proxy-player` (model API and the world only, as today) | the `workspace` volume read-write (the repo checkout, persisted), the CLI home, the shared Claude login and the player's MCP token as environment variables |
| `proxy-player` | the existing egress proxy | `inside` and outside | nothing |
| `keeper` | the keeper loop (user `keeper`): bundle, gate, push | `keeper-net` only, through `proxy-keeper` | the deploy key (a Docker secret mounted in this service only), its own private clone volume `keeper-clone`, the `workspace` volume **read-only** |
| `proxy-keeper` | a second squid with its own allowlist | `keeper-net` and outside | nothing; allows only `CONNECT ssh.github.com:443` |

The character's container never has the deploy key, a git credential or a route to GitHub; the keeper's container never has the Claude login, the MCP token, a route to the model API or the world, and never runs or reads anything the character can make it execute.

**Volumes (per player).** `geldar-ws-<id>`: the repo checkout, persisted across restarts (the source of truth, replacing today's per-session copy); `geldar-cli-<id>-claude`: the CLI home; `geldar-sup-<id>`: supervisor state (`status.json`, `costs.csv`, `supervisor.log`, `STOP`, the lock), written by the supervisor, owner-only inside the player container, never readable by the character's user; `geldar-keep-<id>`: keeper state (`status.json`, `HELD`, `last-pushed-head`), written by the keeper, mounted **read-only** into `player` so the supervisor can read it; `geldar-clone-<id>`: the keeper's private clone, in `keeper` only. The first `start` populates `geldar-ws-<id>` once from a host clone with the existing `prepare` logic (the host clone uses the owner's credentials once, for the initial checkout); after that the volume is the player's own.

**The supervisor** (`packages/supervisor`, TypeScript, in the kit image, one implementation for both host OSes): the behaviour of `run.sh` (decision 60): the continuation text built from the previous stream's last words (`run-summary`), the daily cost cap from `costs.csv`, exponential backoff, five-failure auto-STOP, a held or rejected keeper state stops it (`HELD` is read from the keeper's read-only state: never play on top of an unpushed, rejected history), `STOP` and stop signals end it after the current run, one run at a time, status files after every step. It starts each run as the `player` user with the headless session mode, the model settings and the shared login. The director (wave 12) is a function of this process.

**The keeper** (`packages/keeper`, TypeScript, in the kit image): every `GELDAR_KEEPER_INTERVAL` seconds (default 600; also right after a run ends when the supervisor drops a request file the keeper may read; the keeper never trusts the request's content), it treats the workspace as untrusted data exactly as today's host does: it builds a bundle of the committed state **in a throwaway clean clone it makes with hardened git** (`GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `GIT_CONFIG_NOSYSTEM` pointing at nothing, `core.hooksPath` to an empty directory, `core.fsmonitor=false`, `protocol.file.allow=user` only for the one local fetch, `uploadpack.allowAnySHA1InWant` off, no `--recurse-submodules`, no `includeIf`), fetches the workspace's committed history into `keeper-clone`, runs the existing gate (`geldar-verify`: memory-only paths, size caps, identity rules, the history checks) on the new commits, and pushes **fast-forward only** (never `--force`, never `+refs`) over SSH with the deploy key to the repo's default branch. Uncommitted memory the character left is committed first by the existing save step (`geldar-git`, run as the `player` user by the supervisor at the end of each run, with the message `session end: unsaved memory` as today), never by the keeper. A gate rejection, a non-fast-forward, an auth failure or a hash mismatch writes `HELD` with a short reason and stops pushing until a person clears it; nothing is retried blindly. A push needs a changed HEAD; no change, no push.

**The deploy key.** `geldar-play deploy-key <id>` (owner action, host side): `ssh-keygen -t ed25519` into `<state>/<id>/keeper/` (private key 0600, directory 0700), registers the public key on the repo with write access (`gh api repos/<repo>/keys`, title `geldar-<id>`), and records the repo. The private key reaches only the `keeper` service as a Docker secret. GitHub's SSH host keys are pinned in the kit image (checked against GitHub's published fingerprints at release; updating them is a release change), `StrictHostKeyChecking yes`. A revoked or rotated key is `deploy-key --rotate` then `restart`.

**Egress.** `proxy-player` keeps today's allowlist (the model API and the world's host and port). `proxy-keeper` allows `CONNECT ssh.github.com:443` and nothing else, no DNS for anything else; the keeper's SSH uses `ProxyCommand` with an HTTP CONNECT helper. The two proxies share no state.

**Hardening (every service):** `cap_drop: [ALL]`, `no-new-privileges`, read-only root filesystem with explicit tmpfs, non-root users, CPU, memory and pids limits, no Docker socket, no privileged mode, no host network, `restart: unless-stopped` with a health check each (the supervisor writes a heartbeat; the keeper writes its last-run time), no published ports.

**What stays the same:** the template and the character's view (decisions 40, 55, 58; no meta words); the host-side `play`, `run` and `setup` verbs keep working for owners who do not want a persistent group; the post-session gate code is shared, not copied.

**Honest limits.** The keeper reads and fetches a repository the character wrote to: a malicious repository is the main attack on it, which is why it fetches into a private clone with hardened git and runs the gate before any push, and why the hostile tests of SC-164 are a gate for this wave. A deploy key that leaks lets its holder push to that one repository (and nothing else); the gate on the keeper side limits what the character can make it push, but not what a thief of the key could push. Docker Desktop on Windows runs the group in its VM; the key is stored in a Docker secret from a file on the host, owner-only.

## SC-160: `geldar-supervisor` (Sonnet; kit)

- **Branch** `scriptorium/sc-160-supervisor`. Depends on: SC-120 (run-summary), SC-122 (the behaviour to port).
- **Files:** a new package `packages/supervisor/` (TypeScript, same layout and tooling as `packages/verify`; a `geldar-supervisor` binary), tests, `image/Dockerfile` (install the binary), `pnpm-workspace.yaml` if needed.
- **Behaviour:** port `launcher/lib/run.sh` exactly (read it and its tests first; decision 60 and its review fixes are the spec): the continuation text byte for byte, the daily cap (UTC day, `costs.csv` columns `run,utc,turns,cost`), backoff and caps with the same defaults and bounds from the same `GELDAR_RUN_*` environment names, five-failure auto-STOP (`auto: ...` first line), STOP (`manual` cleared at start, `auto:` kept), one supervisor lock, signals (SIGINT, SIGTERM, SIGHUP: stop after the current run, never kill a running one), status files under `/state/supervisor`. Differences: each run is a child process started as the `player` user (uid 1000) with `claude --autocompact 100000 --settings /etc/geldar/settings/play.json -p <prompt from a 0600 file in /state/supervisor> --max-turns <n> --output-format stream-json --verbose` (plus `--model` from `GELDAR_RUN_MODEL`), its stdout saved to `/state/supervisor/session-<n>.jsonl` (the character's user cannot read `/state/supervisor`); after each run it runs the existing save step (`geldar-git` unsaved-memory commit, as the `player` user) and drops a `checkpoint-request` file for the keeper; it reads `/keeper-state/HELD`: present means stop with `auto: the keeper held the history` and never play on top of it; a heartbeat file for the health check. The director hook is a no-op function in this packet (wave 12 plugs in).
- **Test:** unit tests with a fake child process and a fake clock (no docker): every behaviour of the run.bash tests ported (backoff, caps, STOP kinds, lock, signals, continuation text with the hostile fixture, cap sleeping to the next UTC day), plus HELD stops it, the child runs as the right uid (assert the spawn options), the prompt file mode, no token in arguments or logs. **Revert checks:** ignore HELD; drop the failure cap.

## SC-161: `geldar-keeper` (Sonnet; kit)

- **Branch** `scriptorium/sc-161-keeper`. Depends on: none (reuses `packages/verify` and `launcher/lib/bundle.sh` logic as the reference).
- **Files:** a new package `packages/keeper/` with a `geldar-keeper` binary, tests with local bare repositories, `image/Dockerfile` (install, `openssh-client`, a CONNECT helper script, the pinned `known_hosts`), a data file of GitHub's pinned SSH host keys.
- **Behaviour:** the keeper loop of the Design: every interval (and on a `checkpoint-request`), build a throwaway hardened fetch of the workspace's committed history into `/clone`, run the gate (import the gate from `packages/verify`: do not copy it) on the new commits against the repo's current remote HEAD, push fast-forward only with the deploy key through the proxy (`GIT_SSH_COMMAND` with the key, `StrictHostKeyChecking=yes`, the pinned `UserKnownHostsFile`, a `ProxyCommand`), write `/keeper-state/status.json` and `last-pushed-head`, write `HELD` with a reason on any rejection, failure or hash mismatch and stop pushing until `HELD` is removed. The remote URL, the key path, the interval and the paths come from environment variables with the names fixed in the contract (`GELDAR_KEEPER_REMOTE`, `GELDAR_KEEPER_KEY`, `GELDAR_KEEPER_INTERVAL`, `GELDAR_KEEPER_WORKSPACE`, `GELDAR_KEEPER_CLONE`, `GELDAR_KEEPER_STATE`); a `file://` or bare-repo remote works in tests.
- **Test (the hostile ones are the point):** a workspace repo with hooks (`pre-push`, `post-checkout`, `post-merge`), a hostile `.git/config` (`core.fsmonitor`, `core.sshCommand`, `core.hooksPath`, `includeIf`, `url.<x>.insteadOf`, `credential.helper`), symlinks and a symlinked `.git`, submodules, a huge blob, a history rewrite (non-fast-forward), force-push attempts, paths outside memory, a gate rejection, a remote that rejects, a remote that moved: each ends in a refusal or a clean fast-forward and never executes anything from the workspace and never pushes more than the gate allows; no `--force` anywhere (grep test); the deploy key never appears in logs or arguments; a good change pushes once and a repeat with no change pushes nothing. **Revert checks:** drop the hooks override; allow a non-fast-forward.

## SC-167: pulling upstream changes into the player (Sonnet; kit)

- **Why (owner, 2026-11-11):** when the player repo changes upstream (a merged `geldar-play upgrade` pull request with new template files, an owner edit), the running player must pick it up. Today `upgrade` opens a pull request that the owner merges; nothing carries the merge into a running container.
- **Branch** `scriptorium/sc-167-upstream-sync`. Depends on: SC-160, SC-161.
- **Design:** (1) the keeper, which already holds the deploy key and the private clone, also fetches `origin` each interval (read only) and, when the remote default branch has commits the workspace does not have, runs a check on them (fast-forward of what the workspace already pushed; at most N commits and M megabytes; no symlink, submodule or path-escaping entry; nothing deleting or rewriting `memory/` history) and writes them as a bundle plus a small manifest into its read-only state volume (`/keeper-state/upstream.bundle`, `upstream.json` with the new HEAD). (2) The supervisor, only BETWEEN runs and only when the workspace has no uncommitted changes, applies the bundle as the **`player` user** (the character's own privileges, so anything an agent-planted hook or config could do gains nothing): hardened git (config isolation, `core.hooksPath` to an empty directory, `core.fsmonitor=false`, no submodules), `git fetch <bundle>` then `git merge --ff-only`; if the workspace has local unpushed commits ahead, a rebase of those memory-only commits onto upstream; on any conflict or failure it aborts cleanly, writes `HELD` with `upstream sync: <reason>` through the supervisor status and stops, never merging by hand. (3) The new files take effect at the NEXT run start (template files such as the skills and instructions are read at session start), never mid-session. (4) `geldar-play sync <id>` triggers an immediate keeper fetch and apply; `status` shows the last upstream HEAD and the last sync result; nothing about it is character-visible.
- **Test:** a bare remote that moves ahead with template changes: the workspace fast-forwards between runs and not during one; local unpushed commits are rebased on top; a conflicting upstream change is held, not merged; upstream commits that add a symlink or touch `memory/` history are refused; a malicious upstream bundle or an agent-planted hook in the workspace executes nothing outside the `player` user's own privileges; repeated sync with no change does nothing. **Revert checks:** apply mid-run; use a non-fast-forward merge.
